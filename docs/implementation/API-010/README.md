## Безопасное исправление ранее сохранённых длинных заметок

`backend/scripts/repair_note_chunks.py` — отдельная ограниченная команда оператора.
По умолчанию она **только показывает план** для одного явно выбранного workspace
и существующего owner. Автоматического изменения production при deploy/startup нет.
Инструмент не читает `.env`, credential stores или другие DSN: подключение задаётся
отдельной переменной `NOTE_REPAIR_DATABASE_URL` из существующего защищённого окружения.
Принимается только готовая БД с ограниченной runtime-ролью flare_app; членство и owner
проверяются под RLS. Привилегий superuser/migration-owner не требуется и они отклоняются.

Кандидаты: активная ready-версия ручной note с parser_version manual-note-v1, хотя бы
одним chunk больше4000 UTF-8 байт и суммарным содержимым не больше800000 байт. Последняя
граница соответствует уже существующему HTTP-максимуму200000 Unicode-символов. Другие
источники, удалённые/processing записи и данные за пределами этого контракта не
ремонтируются этим инструментом. Для них нужен отдельный разбор; импорт, voice и URL
не переписываются.

Dry-run выводит только bounded список ID/версий/размеров: **без текста, заголовков,
имён, адресов или DSN**. По умолчанию до25 кандидатов; явный limit допускает1..100.

Применение требует флага `--apply`:

1. Для каждой записи отдельно короткая транзакция блокирует document, повторно
   проверяет текущий version token, тип, состояние, размер и права. Изменившаяся или
   уже исправленная запись пропускается. Планы одного owner не дают доступ к другой
   рабочей области.
2. Создаётся **новая** версия с точным прежним текстом, заголовком, metadata и автором.
   Текст делится существующим UTF-8 splitter на chunks до4000 байт.
3. Только после вставки всех chunks новая версия становится current. Сбой откатывает
   эту запись целиком. Старые ready-версии/chunks/evidence не меняются и не удаляются.
4. Две попытки одного плана создают максимум одну новую версию. Повторная команда
   безопасна: исправленные записи больше не попадают в план.
5. Нет запуска AI, изменения расписания/квоты, нового capture event или запроса
   провайдеру. Обычная следующая scheduled selection увидит подготовленные chunks.
   Действующие Team-права/лицензия/лимиты записи не обходятся.

Каждый SQL ограничен timeout5с и lock timeout500мс; pool acquisition3с. В цикле записи
chunk проверяется deadline30с на заметку. Транзакция отдельной заметки атомарна;
предыдущие успешно завершённые заметки в пачке сохраняются при последующем сбое.
В этом случае команда выдаёт безопасную ошибку и предлагает снова выполнить dry-run.
План при `--apply` строится заново, а token проверяется непосредственно перед записью.

### Для оператора после обновления сервера

Использовать matching main checkout с установленными backend dependencies. Передать
`NOTE_REPAIR_DATABASE_URL` через существующий защищённый способ, не вставлять DSN в
аргументы, переписку или логи. UUID workspace и ID существующего owner получить из
разрешённого оператору контекста. Затем:

```sh
python backend/scripts/repair_note_chunks.py --workspace WORKSPACE_UUID --user OWNER_USER_ID --limit 25
python backend/scripts/repair_note_chunks.py --workspace WORKSPACE_UUID --user OWNER_USER_ID --limit 25 --apply
python backend/scripts/repair_note_chunks.py --workspace WORKSPACE_UUID --user OWNER_USER_ID --limit 25
```

Проверить план и резервную копию по обычной процедуре OPS до применения. Повторять
bounded пачки, пока planned не станет0. Команду запускают отдельно для каждой
согласованной рабочей области. Не менять роли, дневные слоты, историю или лимиты
ради прохождения repair. Production-подключение и запуск этой команды в данном
изменении **не выполнялись**: они требуют доступ оператора, который есть у Вовы.

## Открытие исходной версии из Flare

- Evidence API дополнен `documentVersionId`, `versionNumber`, `versionCreatedAt`,
  полученными из существующего immutable source join. Генерация и сохранение Flare
  не менялись; новая миграция не требуется, schema остаётся0025.
- Read-only `GET /items/{item}/versions/{version}` возвращает item projection на
  запрошенный момент, savedAt и isCurrent. Внутренний item.currentVersionId — ID этой
  snapshot-проекции; frontend не использует его для редактирования текущей заметки.
  Ответ no-store. Чужие/удалённые/непубликованные и отсутствующие версии одинаково
  недоступны; item/version должны принадлежать друг другу.
- Обе ссылки из карточки evidence ведут на item+version в том же проекте. Существующее
  окно Vault показывает исходный текст, автора, номер версии и дату. В этом режиме
  отсутствуют Edit/Delete. Кнопка «Open current version» ведёт в обычный редактор
  актуальной заметки. Изменение текущей заметки не меняет старый Flare/цитату.
- Закрытие окна убирает item и version из адреса, сохраняя project и остальные
  параметры. Epoch guards не дают позднему ответу открыть закрытое окно или заменить
  другую выбранную заметку. Ошибка источника отделена от состояния общего списка:
  успешный list refresh не скрывает отсутствующий исходный документ.
- В режиме старого API evidence без version ID сохраняет старую ссылку на текущую
  заметку. При явном version ID отсутствующий snapshot **не подменяется** текущим.
  В локальном mock-провайдере не выдумываются старые версии, которых он не хранит.
- Английский/испанский текст и даты локализованы. Дизайн следует существующему sheet;
  reference lock и принятые решения находятся в [design.md](design.md).

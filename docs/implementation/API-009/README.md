Дата: 16 октября 2026. Проверяемый код: `6f6504297b906035af62244342b134e675b04e96`.
Аудит выполнен на свежем main в отдельной ветке. Изменения API-005 и GROWTH-003,
которые параллельно делает Вова, не затронуты.

в проекте больше нет ошибок: ниже отдельно перечислены оставшиеся решения,
внешние проверки и ограничения доказательств.

## Результаты и воспроизводимость

[Полный зелёный CI](https://github.com/VladimirMalevanik/flare/actions/runs/38812087247)
проверяет точно `6f65042`:

- self-managed PostgreSQL: **1373 passed, 1 skipped**;
- managed/Yandex-compatible PostgreSQL: **1372 passed, 2 skipped**;
- frontend: **341 passed** + **24 scheduled-analysis passed**;
- ESLint, production build, pip check, миграционные сценарии и voice runtime: passed;
- [отдельный Linux standalone artifact](https://github.com/VladimirMalevanik/flare/actions/runs/38812127418): passed, SHA файла RELEASE_SHA и checksum архива сверены перед запуском.

Skipped-кейсы не выдаются за проверки: в self-managed пропущен managed-owner тест,
в managed — две проверки self-managed executor/ownership. Новых skip или
ослабления продуктовых assertions не добавлено.

Доказательства до исправления:

- [Первое воспроизведение](https://github.com/VladimirMalevanik/flare/actions/runs/38809705462): обе БД подтвердили недопустимый текст/одиночные длинные chunks; клиентские гонки и зависания тоже были красными.
- [Дополнительные регрессии](https://github.com/VladimirMalevanik/flare/actions/runs/38810887050): защита черновиков и срок auth до реализации.
- Локальная регрессия двойного PATCH перед исправлением: `2 !== 1`; после — один PATCH.

Обычный UI-тест shortcut раньше дважды вызывал один и тот же Capture с незавершённым
сохранением и ожидал две записи. Для сохранения смысла keyboard-теста каждый shortcut
теперь проверяется в отдельном экземпляре, по одной записи. Отдельный новый тест
явно запрещает дубли при незавершённом запросе. В старых auth-тестах добавлена загрузка
настоящего общего deadline helper; проверки согласий и подтверждения почты сохранены.

Локально дополнительно подняты две новые PostgreSQL17 с pgvector на58491/58492.
Миграции и rollback-sensitive сценарии работают с синтетическими tenants.
Новые **22 backend-регрессии прошли**. Полный локальный прогон дал
1368/1367 passed и пять ошибок окружения: subprocess-тесты сбрасывают PYTHONPATH,
поэтому не видят переиспользованные библиотеки, а PYTHON_DOTENV_DISABLED мешает
тесту загрузки dotenv. Эти пять сценариев прошли в полном штатном CI. Их не
пропускали и не переписывали ради зелёного результата.

В исходном baseline один CI упал при скачивании ffprobe по внешнему timeout;
это не исправлялось изменением продукта. В итоговом CI скачивание и runtime-проверка
успешны.

## Что оставлено для решения или проверки

### 1. Обновить production-зависимости перед широким выпуском

`npm audit --omit=dev --package-lock-only` обнаружил три пакета: next16.3.4
(package severity critical), sharp0.35.4 (high), source-map-js1.2.1 (high).
Это результаты advisory database, а не доказательство эксплуатации Flare.

| Пакет | Конкретный следующий шаг | Применимость |
| --- | --- | --- |
| next16.3.4 | Согласовать обновление Next и согласованного eslint-config-next до16.3.8 или более нового совместимого исправления, затем пересобрать обе матрицы/artifact. | [RCE advisory](https://github.com/advisories/GHSA-vcvr-r3jv-pc5j) требует Node ImageResponse с атакующим SVG. В Flare не найдены next/og/ImageResponse; OG статический. Это конкретное RCE в приложении не воспроизведено. Другие [self-hosted cache advisories](https://github.com/advisories/GHSA-4jqv-mc3x-m676) требуют отдельного внимания: проект размещается самостоятельно, даже при динамических/no-store страницах. |
| sharp0.35.4 | Поднять resolved sharp до0.35.5 или исправленной совместимой версии через lockfile после проверки дерева. | [librsvg advisory](https://github.com/advisories/GHSA-wq5f-xc86-pv6w). Найденное использование next/image — статический брендовый SVG с unoptimized. Путь обработки пользовательского SVG не найден. Это не отменяет обновления. |
| source-map-js1.2.1 | Поднять resolved версию до1.2.2 или исправленной совместимой. | [DoS advisory](https://github.com/advisories/GHSA-68fv-2mgg-jv7q). Публичного приёма source maps в Flare не найдено; package advisory остаётся. |

Обновления не применены: личные правила владельца требуют подтверждения для изменений
production-зависимостей. Не выполнялись npm audit fix, установка новых runtime пакетов
или изменение lockfile. Подготовлены версии и объём проверки; отдельного вопроса
ночью не задавалось. Перед обновлением ещё раз сверить свежие advisories и доступные
версии. Backend проверен pip check; полный SCA всех backend-транзитивных пакетов
этим не заменяется.

### 2. Старые большие ручные заметки

Исправление действует при создании и при фактической замене текста. Уже сохранённые
старые большие chunks автоматически не переписаны, поскольку это меняет историю
источников. Прежде чем делать backfill, нужно получить согласие на ограниченный repair:
сначала только посчитать affected items, затем создать новые версии с точным текстом,
сохранить авторов и старые evidence, не запускать AI автоматически. Реальные данные
для такого подсчёта в этом аудите не читались.

### 3. Проверить полезность реального анализа — API-005, Вова

Fake AI проверяет plumbing, точные цитаты, доступ и пустые/ошибочные состояния;
он не доказывает полезность настоящего Flare. Случай друга/Ильяса и критерии принятия
явных решений остаются в активной API-005. Нельзя обещать, что исправление chunking
решило именно его ситуацию, без исходной диагностики владельца.

### 4. Исторический источник по ссылке из Flare

Сохранённый Flare правильно сохраняет исходную цитату, но ссылка передаёт itemId
и открывает текущую версию заметки. После редактирования эта версия может уже не
содержать старую цитату. Потеря самого evidence не обнаружена. Нужно выбрать продуктовый
вариант: просмотр исходной версии из Flare либо явная подпись об изменённом источнике.
Новый version-viewer и API не добавлялись без этого решения.

### 5. Проверить серверные условия, не включать сервисы вслепую

- Существующие OPS-006 evidence в main описывают отдельный серверный smoke. Этот
  аудит не даёт новой гарантии для SMTP deliverability, OAuth consent внешних
  источников, production AI или checkout. Team и generic Sources, выключенные
  оператором, не включались; почтовые allowlist и цены не придумывались.
- Подтвердить edge/proxy body limits, slow-body deadlines и rate limiting для auth
  и обычного JSON: отдельный TeamBodyLimit покрывает Team/campaign writes, но общего
  app-level middleware для остальных JSON не найдено. Возможно, это обеспечивает
  серверная граница. Конфигурация Azure/WAF не читалась; уязвимость сервера не
  объявляется доказанной. Нагрузочный тест production не выполнялся.
- При полностью остановленном import worker запрос может оставаться в очереди,
  пока worker не восстановится/не обработает expiry. В браузере проверена ручная
  отмена. Нельзя выдавать конечный автоматический таймаут processing за гарантию
  работы очереди при мёртвом worker. Нужен операторский контроль readiness/import
  jobs+cleanup; отдельный UX порога «ожидает слишком долго» потребует выбора срока.
- Проверить matching API/web/workers SHA, миграцию0025, worker readiness, одну
  тестовую заметку → scheduled Flare/понятный нулевой результат и реальную доставку
  только на согласованный проверенный адрес после деплоя.

Дополнительные ограничения, не дефекты этого исправления: у исторических/provider/ZIP
источников без сохранённого creator автор не выдумывается; экспорт allowlist не включает
автора. Если нужен гарантированный creator у ZIP и в переносимом экспорте, это отдельное
согласованное расширение provenance. Редактирование имени/email в Settings не объявлено
багом: для авторизованного аккаунта поля уже readOnly.

## Интеграция

Нет новой миграции, изменения квот, runtime-зависимости, production-конфигурации,
доступа к секретам, реальной почты/оплаты/провайдера или деплоя. Интеграция проверенной
ветки разрешена прежней инструкцией владельца. Само слияние не означает принятие
продуктовых решений выше, включение сервисов или подтверждение работы новой версии
на сервере. API-009 передаётся на проверку владельцу; статус done без его приёмки
не устанавливается.
